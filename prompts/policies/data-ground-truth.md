# Laboratory ZIP data ground truth

## Purpose

This document is the **single format ground truth** for the laboratory ZIP consumed by LabFlow. It describes what can exist in the archive, how the files relate to each other, and which fields are evidence versus interpretation. The deterministic parser and every AI OPERATION receive this same ground truth.

The source ZIP is immutable. A path, filename, header, unit, value or relationship that is not present in RAW evidence must never be presented as a measured fact.

## Archive model

A normal experiment is a ZIP containing one experiment root directory. Under it there may be:

- root-level JV summary tables;
- sample/device directories;
- one or more run/time directories below each sample/device;
- per-run JV, Parameters and Tracking text files;
- unknown or auxiliary files, which remain in the manifest even when LabFlow does not parse them.

The archive does **not** need to be perfectly conformant. Missing summaries are allowed when individual JV files provide usable evidence. Repeated runs are allowed. Different samples/devices, groups, references, formulations and process variants may coexist in the same ZIP and must not be collapsed into one entity merely because they share a file layout.

## Known file families

### Root summaries

- `JV Summary.txt` — optional general summary.
- `JV Summary_Parameters FW.txt` — forward-scan summary.
- `JV Summary_Parameters RV.txt` — reverse-scan summary.

The FW/RV parameter summaries are tab-separated. The canonical columns are:

1. source file name
2. Voc (V)
3. Jsc (mA/cm²)
4. VMPP (V)
5. JMPP (mA/cm²)
6. PMPP (mW/cm²)
7. Rs (Ohm)
8. Rsh / R// (Ohm)
9. FF (%)
10. Efficiency (%)

### Individual run files

Recognized markers are:

- `Stability (JV)` — JV metrics and raw forward/reverse curves;
- `Stability (Parameters)` — acquisition/device parameters and metadata evidence;
- `Stability (Tracking)` — tracking/time-series metadata evidence.

All are currently expected to be `.txt` files. Unknown `.txt` files are retained in the manifest but are not silently reclassified.

## Individual JV text layout

Observed JV files are tab-separated and can contain:

- comment markers such as `## Header ##` and `## Data ##`;
- bracketed metadata sections such as `[General info]`, `[JV Settings]`, `[Cell Settings]`;
- `key<TAB>value` metadata rows;
- a metric table beginning with a row equivalent to `Scan<TAB>Voc<TAB>Jsc...`;
- scan rows labelled `FW` and `RV`;
- a raw-curve table beginning with a row equivalent to `V_FW (V)<TAB>J_FW...` and containing FW/RV voltage-current-density pairs.

The metric fields are Voc, Jsc, VMPP, JMPP, PMPP, Rs, Rsh/R//, FF and Efficiency. Curve points are RAW evidence and are never generated by AI.


## Parameters text layout

Observed `Stability (Parameters)` files are tab-separated acquisition logs. They can contain:

- `## Header ##` / `## Data ##` markers;
- `[General info]` with fields such as `User`, `Device`, `Cell area (cm2)`, `Test`, `Date`, `Time`, `Note`;
- `[JV Settings]` with acquisition settings such as `Vmin`, `Vmax`, voltage step, scan rate, automatic Voc, scan direction, voltage/current range and auto-range flags;
- `[Cell Settings]` with device/cell descriptors such as typology, cell area and channel/cell counts;
- a time-series table starting with `Time (Hours)` followed by FW/RV performance fields.

Parameters files are evidence for acquisition conditions, device identity and longitudinal performance. A repeated value in this file must not automatically overwrite a value measured in a dedicated JV file when the two sources conflict; the conflict becomes a review item.

## Tracking text layout

Observed `Stability (Tracking)` files are tab-separated maximum-power-point tracking logs. They can contain:

- the same `[General info]` identity block;
- `[Tracking Settings]` with fields such as tracking algorithm, `dV track (V)`, track delay, JV interval and test duration;
- `[Cell Settings]`;
- a data table beginning with `Time(Hours)` and typically containing `Voltage(V)`, current density and power.

Tracking files are time-series evidence. They can support stability/process interpretation and Design context but must never be converted into synthetic JV curves.

## File-format and conversion contract

“Conversion” means converting RAW evidence into LabFlow's canonical **in-memory interpretation**. It never means rewriting, renaming or replacing a source file. Every converted value retains the RAW path, source field/header, original text and conversion method in provenance.

| RAW family | Physical format | Required structure | Canonical conversion | Forbidden conversion |
|---|---|---|---|---|
| ZIP archive | ZIP container | One normal experiment root; unknown entries allowed | Manifest entries with verbatim paths and detected family | Dropping unknown files or rewriting paths |
| FW/RV summary | UTF-8-compatible `.txt`, tab-separated | Header plus at least 10 fields: file, Voc, Jsc, VMPP, JMPP, PMPP, Rs, Rsh, FF, efficiency | One directional metric record per row, linked by source filename | Inventing curve points or merging unmatched rows |
| Individual JV | UTF-8-compatible `.txt`, tab-separated sections | Metadata sections, FW/RV metric rows and optional four-column curve table | Measurement with separate `fw` and `rv` metrics plus RAW curve points | Synthesizing a missing direction or curve |
| Parameters | UTF-8-compatible `.txt`, tab-separated sections | General/JV/Cell settings and optional time-series table | Auxiliary acquisition/device evidence linked by device/time/path | Overwriting dedicated JV metrics without review |
| Tracking | UTF-8-compatible `.txt`, tab-separated sections | General/Tracking/Cell settings and time/voltage/current/power table | Auxiliary MPP time-series evidence | Converting tracking points into a JV curve |
| Unknown/auxiliary | Any retained ZIP entry | No assumed schema | Manifest-only evidence until explicitly classified | Guessing a known family from content resemblance alone |

### Canonical field names

- Direction: `FW` → `fw`, `RV` → `rv`; an absent direction stays absent.
- Metrics: `Voc` → `voc`, `Jsc` → `jsc`, `VMPP` → `vmpp`, `JMPP` → `jmpp`, `PMPP` → `pmpp`, `Rs` → `rs`, `Rsh`/`R//` → `rsh`, `FF` → `ff`, `Efficiency`/`PCE` → `eff`.
- Curve columns: `V_FW (V)` → `v_fw`, `J_FW` → `j_fw`, `V_RV (V)` → `v_rv`, `J_RV` → `j_rv`.
- Empty strings, non-finite numbers and explicit missing markers become `null`/unknown; they never become zero.
- Decimal-comma parsing is a mechanical fallback only when a token contains one comma and no decimal point. Record the fallback in provenance.
- Units remain exactly as evidenced. Mapping a different unit or applying a scale factor is a reviewable patch, not a silent parser conversion.

### Format-review evidence

For each detected family, an AI format review must report: representative RAW paths, delimiter, encoding confidence, section/header markers, observed columns, explicit units, numeric convention, canonical target, applied mechanical conversions, unresolved ambiguities and forbidden conversions. A family not evidenced in the supplied context must be reported as `not_observed`, not assumed present.

## Identity and relationships

A **measurement** represents one JV measurement source and may contain FW only, RV only, or a matched FW/RV pair.

A **sample/device identity** is established from evidence in this order:

1. explicit internal device metadata (for example `General info.Device`);
2. matching summary row;
3. JV filename;
4. parent sample directory;
5. related Parameters/Tracking files;
6. repeated naming convention elsewhere in the same ZIP.

A **group** is a working classification derived from the sample/device identity or explicit metadata. It is not a new physical fact.

`REF` is treated as a reference marker only when it is a clear standalone token/prefix in the source evidence.

The same ZIP may contain many samples/devices and many groups. Design reconstruction must consider all of them. If evidence suggests different stacks, solutions or process variants for different devices/groups, they must be represented separately rather than merged into one generic design.

## Experimental-design evidence

Design information can be:

- `user_confirmed` — explicitly entered/confirmed by the user;
- `raw_evidence` — explicitly present in RAW files/metadata;
- `ai_inferred` — a hypothesis supported by evidence but not explicitly present;
- `unknown` — not established.

Solutions/formulations, device stacks and process conditions may be one-to-many. A solution can be associated with multiple device variants; a device variant can reference multiple solutions. LabFlow must retain the association and provenance.

## Numeric and unit rules

- Primary delimiter: tab (`\t`).
- Decimal point is expected; decimal comma may be accepted as a parsing fallback.
- Units are taken from explicit headers/metadata when available.
- Mojibake/replacement glyphs can appear in unit labels; parsing should rely on stable field semantics before exact glyph rendering.
- Never change a unit, scale a scientific value or fabricate a missing number without an explicit reviewed working-state patch.

## Missing and partial data

- Missing FW or RV summary files do not invalidate the experiment.
- Individual `Stability (JV)` files are the preferred deterministic fallback.
- Parameters/Tracking files provide metadata/evidence, not invented JV values.
- Partial measurements remain partial; unknown values remain unknown.
- All RAW paths remain traceable in provenance.

## AI constraint

For every OPERATION, this ground truth is authoritative for the ZIP/data model. The model must inspect all supplied entities, not only the first example. It must never collapse multiple devices/solutions/design variants into one without evidence. If context is insufficient, return `unknown` or an explicit unresolved item.
