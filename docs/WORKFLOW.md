# LabFlow workflow and operating model

This is the primary architectural guide for LabFlow. Read this before changing the data model, Action system, Review, Design, Results, Report, NOMAD or AI context logic.

LabFlow is intentionally built around one simple researcher workflow:

```text
Upload ZIP
   ↓
Deterministic import + analysis
   ↓
Review / correct the current Working Copy
   ↓
Inspect deterministic Results
   ↓
Complete Experiment Design
   ↓
Generate or edit the Report
   ↓
Prepare NOMAD export
   ↓
Explicitly save/export
```

The important rule is that the uploaded ZIP is **source evidence**, not the editable experiment model.

---

## 1. The five layers of LabFlow data

LabFlow separates five concepts that must never be collapsed into one another.

```text
1. ORIGINAL SOURCE
   immutable uploaded ZIP bytes
             ↓
2. WORKING COPY
   one editable in-memory scientific experiment
             ↓
3. CANONICAL STORE
   deterministic semantic identity / evidence / relations over the Working Copy
             ↓
4. ANALYSIS DOSSIER
   compact deterministic summary of the current revision
             ↓
5. RESEARCH CONTEXT PACK
   bounded request-specific context for Chat and AI assists
```

### 1.1 Original Source

The file selected by the researcher is cloned byte-for-byte at import time and retained as immutable source evidence.

The original source preserves:

- original ZIP bytes;
- original archive paths;
- original filenames;
- original RAW and auxiliary files;
- provenance needed for auditing and round-trip export.

No Action, manual correction, Design edit, Report edit or NOMAD Action is allowed to mutate the original source.

### 1.2 Working Copy

`LF.State.state.experiment` is the **only editable scientific state**.

Everything the researcher changes is applied here:

- deterministic safe corrections;
- accepted AI correction proposals;
- manual sample or metadata corrections;
- Design edits;
- report text and figure selection;
- other scientific settings belonging to the experiment.

There must never be a second editable experiment projection hidden in a page, Action or export module.

### 1.3 Canonical Store

`LF.CanonicalStore` is a deterministic semantic view over the Working Copy. It is **not another editable copy**.

It provides:

- stable LabFlow IDs;
- canonical sample identity;
- original-name aliases;
- relations between samples, measurements, files, Design and evidence;
- compact evidence items with provenance;
- lookup indexes by ID and alias.

Large RAW arrays and curve points remain in their existing Working Copy/source representation and are not duplicated into a second giant object.

### 1.4 Analysis Dossier

The Analysis Dossier is generated by `dataset.analyze` for the current Working Copy revision.

It contains the information required to understand the dataset quickly:

- counts;
- deterministic status;
- sample inventory;
- measurement inventory;
- open findings;
- safe corrections;
- true semantic ambiguities;
- evidence/relations/alias coverage;
- compact Results summary.

It is a **summary**, not the entire dataset.

A shared **Experiment Brief** is then derived from those deterministic facts. Its deterministic layer covers scope, performance, comparisons, quality, Design coverage and unresolved questions. If the AI provider is configured, internal `analysis.enrich` may add a provenance-marked scientific interpretation layer. That layer is reused downstream and is keyed to a scientific-input signature, so writing Report/Paper text does not invalidate it. AI enrichment failure never blocks import.

### 1.5 Research Context Pack

The Context Pack is built only when Chat or an AI Action needs context.

It contains only the slice relevant to the current request. It is produced deterministically from the Canonical Store and current UI selection.

A Context Pack may include:

- the shared Experiment Brief (deterministic + optional fresh AI enrichment);
- current page and selection;
- selected sample/device/measurement/group;
- compact measurement values;
- deterministic Results summaries;
- directly relevant findings;
- directly relevant evidence;
- current Design record;
- a bounded report excerpt;
- bounded conversation history.

It does **not** send the full experiment or RAW JV curves by default.

## 2. Import lifecycle

Import is the only experiment entry point.

The app always opens on the Upload ZIP screen, even when a workspace was previously saved: the first page is the same empty Upload ZIP page reached after Reset all, and the researcher resumes the saved flow manually via the stepper or Open Review. A previous experiment route is never resumed automatically on reload.

```text
Researcher selects ZIP
        ↓
clone original bytes
        ↓
inventory archive entries
        ↓
classify known file families
        ↓
parse deterministic formats
        ↓
resolve canonical sample identities and aliases
        ↓
build measurements and FW/RV relationships
        ↓
build evidence and relations
        ↓
calculate deterministic Results
        ↓
build Analysis Dossier
        ↓
open Review Data
```

### File naming philosophy

LabFlow must tolerate poor laboratory naming.

A filename is provenance, not automatically the scientific identity of a sample.

Canonical sample identity is resolved in this order whenever possible:

1. explicit identity inside the parsed file;
2. known deterministic filename pattern;
3. deterministic directory/naming evidence;
4. otherwise an explicit ambiguity.

Examples such as these may refer to the same sample:

```text
REF1
REF-1
REF_01
Reference 1
```

LabFlow keeps the originals as aliases and stores one canonical entity when the mapping is deterministic. If it is not deterministic, the uncertainty becomes a finding instead of a silent guess.

## 3. Revision and save model

The Working Copy has a scientific revision.

Scientific mutation advances the revision. Examples:

- applying a safe correction;
- applying an accepted AI proposal;
- manual data correction;
- changing Design data;
- changing scientific report content when report state is part of the current Working Copy.

Read-only Actions do not create a scientific revision merely because they ran:

- Chat;
- AI interpretation of Results;
- accepting/rejecting a proposal before applying it;
- opening pages;
- filtering charts.

### Dirty state

The top bar communicates whether the current Working Copy has changes that have not been saved into a new LabFlow package.

Only **Save** marks the current internal browser representation as saved. **Export** creates a ZIP explicitly.

Derived exports do not clear dirty state:

- Report PDF;
- Report DOCX;
- NOMAD ZIP;
- other derived files.

### Save never overwrites the upload

Export creates a **new file**. Save persists only the internal LabFlow representation. The uploaded ZIP remains immutable.

---

## 4. Action philosophy

A researcher Action exists only if it represents a goal a researcher can understand.

A function is not automatically a Action.

These are examples of **internal services**, not public Actions:

- parse one file;
- calculate Results;
- rebuild Canonical Store;
- validate a proposal;
- apply a proposal;
- rebuild Design evidence;
- validate NOMAD mappings;
- store a Action result.

`analysis.summarize` (§6.1.1) is an internal deterministic Action packaged for Settings → Actions inspectability; it is auto-run, not offered as a public researcher action. `analysis.enrich` is an internal automatic AI enrichment that runs only when a provider is configured and stores the optional scientific layer of the shared Experiment Brief.

Settings exposes every executable Action in Actions. Actions is a filtered view of those same definitions containing only AI-backed Actions; both surfaces edit the same browser-local runtime definition/prompt override.

| Goal | Kind | Main outcome |
|---|---|---|
| Analyze dataset | Automatic · deterministic | current Canonical Store + Results + Analysis Dossier |
| Apply safe corrections | Researcher action · deterministic | provable corrections applied to Working Copy |
| Resolve ambiguities | AI assist | correction proposals or unresolved decisions |
| Infer missing design | AI assist | proposals for missing Design fields of one selected experiment |
| Interpret results | AI assist | scientific explanation of deterministic Results |
| Generate report | AI assist | report/paper Markdown |
| Improve report | AI assist | revised current Markdown |
| Prepare NOMAD export | Researcher action · deterministic | canonical→NOMAD mapping + readiness validation |

`assistant.chat` uses the same Context Builder and is visible in Settings → Actions; it remains a non-mutating Assistant capability.

## 5. Action execution model

Action definitions live in:

```text
actions/<action-id>/action.json
```

AI Actions additionally own:

```text
actions/<action-id>/prompt.md
```

Structured AI Actions may reference a schema in:

```text
actions/schemas/*.json
```

### Sequential execution

A run is always finite and sequential:

```text
Action
  ↓
checkpoint 1
  ↓ success
checkpoint 2
  ↓ success
checkpoint 3
  ↓
DONE
```

There is one active run. There is no background queue and no parallel model fan-out.

### User controls

While running:

- **Stop** aborts the active run.

On failure:

- AI checkpoint retries automatically after 5 seconds;
- retries once more after 10 seconds;
- after those bounded retries, **Retry checkpoint** is available;
- retry resumes the failed checkpoint, not the completed checkpoints.

There is no manual Continue gate between successful checkpoints.

### Provider output

Provider output is closed by default. When opened it must show meaningful streaming data while it arrives and theme-aware formatted Markdown/JSON at completion.

# 6. Detailed Action workflow

## 6.1 Analyze dataset — `dataset.analyze`

**Kind:** automatic / deterministic  
**Provider:** none  
**Prompt:** none  
**Mutation:** no scientific values are changed

### Why it exists

This is the foundation of LabFlow. It establishes what is known before any AI is asked to interpret anything.

### When it runs

- immediately after ZIP import;
- after deterministic or accepted corrections that change scientific data;
- after other scientific mutations that invalidate the dossier/results.

### What it does

Internally it refreshes:

1. canonical identities and aliases;
2. evidence graph;
3. relations;
4. deterministic JV Results;
5. quality/ranking eligibility;
6. findings;
7. safe-fix inventory;
8. true semantic ambiguity inventory;
9. compact Analysis Dossier.

### Output

The current Analysis Dossier for the current Working Copy revision.

### What it must never do

- call a provider;
- invent sample identity;
- change data to make warnings disappear;
- use AI to decide deterministic facts.

### 6.1.1 Analysis Summary Action — `analysis.summarize` (internal, auto-run)

After analysis is fresh, an internal deterministic Action stores the **Analysis Dossier statistics bundle** (`exp.analysisSummary`) on the Working Copy. It is not a public researcher Action: it runs automatically, never needs a trigger, and never mutates scientific fields.

The bundle is the **single deterministic source** for:

- the Results **Compare** per-scan statistics table (FW/RV median±IQR and min–max);
- **Report** statistics and the six figure series;
- the **NOMAD** derived `analysis.json` (analysis + bundle).

Consumers read the bundle only when `LF.AnalysisSummary.fresh(exp)` — bundle `sourceRevision` matching the Working Copy revision — and otherwise fall back to their own deterministic computation so nothing is ever stale.

Report figures are **rasterized on demand**, never on every render: PNG previews and DOCX/PDF exports share one cached set keyed by `(experiment id, revision, figure selection, includeCharts)`. A Working Copy mutation bumps the revision and invalidates the cache automatically.

## 6.2 Apply safe corrections — `dataset.correct-safe`

**Kind:** researcher action / deterministic  
**Requires:** current Analysis Dossier  
**Mutation:** dataset Working Copy

### Why it exists

Some findings have a mechanically provable correction. These do not require AI or human interpretation.

Examples include:

- excluding a measurement already deterministically blocked from rankings;
- assigning a group derived unambiguously from canonical identity;
- applying explicit REF classification rules;
- other corrections for which target, before, after and evidence are unambiguous.

### Checkpoints

1. **scan** — collect current safe fixes;
2. **apply** — validate each target and apply fixes;
3. **commit** — advance revision and rebuild canonical analysis.

### Provenance

Every applied correction must leave a patch record including as applicable:

- target;
- previous value;
- new value;
- source/method;
- reason;
- evidence;
- reviewer/status;
- timestamp.

### Failure rule

If a target is no longer unambiguous, the correction must fail instead of guessing.

---

## 6.3 Resolve ambiguities — `dataset.resolve-ambiguities`

**Kind:** AI assist  
**Requires:** current deterministic analysis  
**Mutation:** none directly

### Why it exists

Only semantic uncertainty that cannot be established deterministically belongs here.

Typical examples:

- two aliases may or may not refer to the same sample;
- a sample/group mapping is semantically unclear;
- REF/non-REF meaning is not explicit enough for deterministic policy;
- a metadata meaning requires interpretation of human notes.

Technical parser warnings, encoding warnings or missing-file facts are **not** AI ambiguities.

### Context

The model receives a bounded ambiguity Context Pack containing only:

- selected unresolved findings;
- directly linked samples/measurements;
- relevant evidence;
- stable LabFlow IDs.

It does not receive the complete ZIP or full experiment by default.

### Checkpoints

1. **collect** — select true current ambiguities;
2. **resolve** — one bounded structured AI call;
3. **store** — save proposals locally.

### Output

Each ambiguity may become:

- a proposed correction;
- `unresolved` when evidence is insufficient.

AI output is a **proposal**, never an authoritative write.

### Applying proposals

Applying a valid proposal is an internal deterministic service:

1. resolve the target against the current revision;
2. verify the `before` state still matches;
3. verify patch type/value;
4. apply to Working Copy;
5. record provenance;
6. refresh deterministic analysis.

---

## 6.4 Infer missing design — `design.infer`

**Kind:** AI assist  
**Scope:** one currently selected experiment/device  
**Mutation:** none directly

### Why it exists

Experiment Design must already be usable before AI. The researcher can inspect and edit known data directly. AI is only for remaining missing fields.

### Deterministic preparation

Before inference, LabFlow already knows or indexes:

- selected sample(s);
- current device record;
- linked measurements;
- formulations/solutions already known;
- stack/process values already known;
- evidence IDs;
- explicit missing-field inventory.

### Context

The model receives only:

- current selected Design record;
- researcher-entered known values;
- missing fields;
- selected sample/measurement summaries;
- linked evidence.

Known or user-confirmed fields are authoritative and must not be regenerated.

### Checkpoints

1. **collect** — build the selected Design Context Pack;
2. **infer** — structured AI proposal;
3. **validate** — verify selected-sample coverage and contract;
4. **store** — retain proposal for review.

### Output

A proposal for missing fields only, with evidence/confidence where supported.

The researcher remains able to edit the Design manually without running the Action.

---

## 6.5 Interpret results — `results.interpret`

**Kind:** AI assist  
**Mutation:** none

### Why it exists

Deterministic code calculates the Results. AI exists only to explain them scientifically.

### Deterministic source

Results already contain, as applicable:

- FW/RV pairing;
- PCE, Voc, Jsc, FF;
- hysteresis;
- ranking eligibility;
- best-by-sample;
- REF/non-REF rankings;
- group statistics;
- anomalies/warnings;
- curve summaries.

### Context

AI receives a compact Results Context Pack:

- summary;
- top REF/non-REF;
- best-by-sample subset;
- anomalies;
- relevant findings.

It does not calculate replacements for deterministic metrics.

### Output

Scientific Markdown interpretation stored separately from source Results.

---

## 6.6 Generate report — `report.generate`

**Kind:** AI assist  
**Mutation:** Report document only

### Why it exists

The model is useful for scientific prose composition, not for inventing measurements.

### Inputs

A deterministic Report Context Pack includes:

- requested document kind;
- deterministic Results summary;
- Design summary;
- findings;
- provenance;
- selected figure configuration;
- other bounded scientific evidence.

### Checkpoints

1. **collect blocks** — deterministically plan bounded document sections;
2. **draft blocks** — model writes each requested section using the shared Experiment Brief and bounded evidence;
3. **merge/store** — ordered sections become the current Report/Paper editor content.

Fresh imports keep both Report and Paper empty. Drafting occurs only after the researcher explicitly chooses Draft.

### Source-of-truth rule

The current Report Markdown editor is the single textual source used by Report exports. PDF/DOCX must not silently regenerate different prose during export.

---

## 6.7 Improve report — `report.improve`

**Kind:** AI assist  
**Mutation:** Report document only

### Why it exists

Revision is the same conceptual Action regardless of whether the researcher wants to improve Methods, Results, Discussion, scientific review or general style.

### Inputs

- current editor Markdown;
- explicit improvement mode;
- deterministic scientific evidence pack.

### Output

Revised Markdown returned to the same editor/source of truth. Common aids (for example tighten, clarify, evidence check) and Report/Paper-specific aids are modes of this Action. Long documents are split by section/block so each model call receives the relevant text plus the same bounded scientific basis.

The Action must preserve factual consistency with deterministic Results and provenance.

---

## 6.8 Prepare NOMAD export — `nomad.prepare`

**Kind:** researcher action / deterministic  
**Provider:** none  
**Mutation:** no scientific source mutation

### Why it exists

NOMAD is a mapping/export problem, not an AI readiness problem.

### Single mapping principle

One Canonical → NOMAD mapping plan must power:

- NOMAD page;
- local validation;
- generated `experiment.archive.yaml`;
- exported `metadata/mapping_plan.json`.

There must never be separate UI mapping and export mapping implementations.

### Checkpoints

1. **prepare** — build explicit field mapping;
2. **store** — retain the revision-scoped mapping plan;
3. **validate** — run authoritative local validation.

### Mapping row

A mapping should be inspectable in terms such as:

```text
LabFlow source → NOMAD field → current value → required? → status
```

### Readiness

- required missing mappings block staging;
- optional missing values remain visible;
- AI never declares NOMAD readiness.

Scientific mutation invalidates stale mapping/staging.

# 7. Assistant Chat

`assistant.chat` is an AI Action exposed in Actions. Its conversation/output settings remain separate, but its executable prompt/contract is edited through the same Action runtime editor. It is read-only with respect to scientific state.

## Context selection

The Context Builder uses:

- user question;
- current page;
- selected measurement;
- selected Design item;
- Results tab and Compare groups;
- query-matched canonical sample aliases;
- relevant open findings;
- linked evidence;
- bounded conversation memory.

Examples:

### Question from Results

> Why is Treatment B worse than REF?

The Context Pack should prioritize group Results, selected groups, anomalies and relevant Design/evidence instead of unrelated files.

### Question from Design

> What is missing for NEW-1A?

The Context Pack should prioritize selected Design, linked sample/measurements and evidence.

### Question from NOMAD

> What blocks the export?

The Context Pack should prioritize mapping readiness, missing fields and validation warnings.

## Budgeting

Chat context and output have their own bounded settings. AI Action output budgets live in their Action contracts. There is no one global output-token budget controlling every Action.

# 8. Review Data workflow

Review must make three categories obvious.

## Deterministic findings

Shown immediately after import.

## Safe corrections

Provable fixes can be applied individually or in bulk. Applying them modifies only the Working Copy and immediately refreshes deterministic analysis.

## Ambiguities

Only true semantic ambiguity is offered to AI. AI proposals can be applied individually/bulk only after deterministic validation.

## Human decisions

If neither code nor AI has sufficient evidence, the item remains visible as needing researcher decision. It must not disappear into a count.

# 9. Results workflow

Results are always deterministic and independent of Design reconstruction.

The page must remain useful even if Design is incomplete or AI is unavailable.

Expected capabilities include:

- Overview;
- rankings;
- REF/non-REF separation;
- all measurements;
- warnings/anomalies;
- individual and overlay JV curves;
- group comparison;
- responsive statistics tables;
- optional AI interpretation layered on top.

`ORIGINAL_REQUEST/jv_analyzer.html` is the functional reference for useful JV analysis behaviour.

---

# 10. Experiment Design workflow

Design is researcher-first.

```text
Deterministic known data
        +
Researcher edits
        +
Optional AI inference for missing fields
```

Use the UI Kit **Single-experiment Design** pattern:

- experiment/device rail;
- selected experiment canvas;
- formulations;
- fabrication/process;
- stack;
- evidence/provenance;
- missing-field status;
- AI proposal only as progressive disclosure.

AI must never overwrite user-confirmed values silently.

---

# 11. Report workflow

The editor is authoritative and starts empty on a fresh import. There is no automatically generated placeholder prose.

```text
Draft / Improve
       ↓
Markdown editor
       ↓
researcher edits
       ↓
select figures
       ↓
PDF / DOCX / other export
```

The text exported must be the current editor content.

Figure selection is explicit and shared across export formats. Available figure types currently include:

- PCE distribution;
- hysteresis distribution;
- best JV curve;
- PCE vs hysteresis;
- top efficiency;
- group comparison.

Derived export does not mark the Working Copy saved.

---

# 12. NOMAD workflow

```text
Current Canonical Store
       ↓
Canonical → NOMAD mapping plan
       ↓
required/optional validation
       ↓
NOMAD staging package
```

The NOMAD package includes audit material such as:

- canonical snapshot;
- mapping plan;
- provenance/patch information;
- schema/entry files as required.

NOMAD export must never reinterpret original filenames independently from the Canonical Store.

---

# 13. Invalidation rules

Derived state must identify the Working Copy revision it belongs to.

Examples of derived state:

- Analysis Dossier;
- Results interpretation;
- Design proposal;
- NOMAD mapping plan/validation;
- other AI proposals.

If the scientific Working Copy changes, stale derived data must be refreshed or explicitly invalidated. It must never silently masquerade as current.

---

# 14. What must remain simple

Do not add:

- a second editable experiment state;
- server-side workflow orchestration;
- background AI jobs;
- provider queues;
- parallel model fan-out;
- manual Continue gates between successful checkpoints;
- AI calculation of deterministic metrics;
- AI NOMAD readiness decisions;
- automatic rewriting of original files;
- hidden autosave that changes the saved revision;
- giant full-experiment AI payloads by default.

When a feature seems to require one of these, first ask whether it can instead be implemented as:

```text
deterministic service
        ↓
Canonical Store
        ↓
bounded Context Pack
        ↓
optional AI assist
```

# 15. Developer verification workflow

After Action, prompt, state, model or UI changes run the repository validators and unit suite:

```bash
python tools/build_prompt_bundle.py
python tools/build_action_registry.py
python tools/validate_action_contract.py
python tools/validate_state_contract.py
python tools/validate_ui_contract.py
python tools/validate_privacy_contract.py
node tests/unit/run.js $(find tests/unit -maxdepth 1 -name '*-test.js' -printf '%p ' | sort)
find assets/js tests -name '*.js' -print0 | xargs -0 -n1 node --check
```

For architectural changes also test at least one real/synthetic ZIP through:

```text
import → Review → correction → Results → Design → Report → Changes → NOMAD → Save / Export
```

The original upload must remain byte-identical throughout.
