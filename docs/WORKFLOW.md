# LabFlow workflow and operating model

This is the primary architectural guide for LabFlow. Read this before changing the data model, Action system, Review, Design, Results, Report, NOMAD or AI context logic.

LabFlow is intentionally built around one simple researcher workflow:

```text
Upload ZIP
   ↓
Deterministic import + analysis
   ↓
Review / correct the current Working Copy
   ↓
Inspect deterministic Results
   ↓
Complete Experiment Design
   ↓
Generate or edit the Report
   ↓
Prepare NOMAD export
   ↓
Explicitly save/export
```

The important rule is that the uploaded ZIP is **source evidence**, not the editable experiment model.

---

## 1. The five layers of LabFlow data

LabFlow separates five concepts that must never be collapsed into one another.

```text
1. ORIGINAL SOURCE
   immutable uploaded ZIP bytes
             ↓
2. WORKING COPY
   one editable in-memory scientific experiment
             ↓
3. CANONICAL STORE
   deterministic semantic identity / evidence / relations over the Working Copy
             ↓
4. ANALYSIS DOSSIER
   compact deterministic summary of the current revision
             ↓
5. RESEARCH CONTEXT PACK
   bounded request-specific context for Chat and AI assists
```

### 1.1 Original Source

The file selected by the researcher is cloned byte-for-byte at import time and retained as immutable source evidence.

The original source preserves:

- original ZIP bytes;
- original archive paths;
- original filenames;
- original RAW and auxiliary files;
- provenance needed for auditing and round-trip export.

No Action, manual correction, Design edit, Report edit or NOMAD Action is allowed to mutate the original source.

### 1.2 Working Copy

`LF.State.state.experiment` is the **only editable scientific state**.

Everything the researcher changes is applied here:

- deterministic safe corrections;
- accepted AI correction proposals;
- manual sample or metadata corrections;
- Design edits;
- report text and figure selection;
- other scientific settings belonging to the experiment.

There must never be a second editable experiment projection hidden in a page, Action or export module.

### 1.3 Canonical Store

`LF.CanonicalStore` is a deterministic semantic view over the Working Copy. It is **not another editable copy**.

It provides:

- stable LabFlow IDs;
- canonical sample identity;
- original-name aliases;
- relations between samples, measurements, files, Design and evidence;
- compact evidence items with provenance;
- lookup indexes by ID and alias.

Large RAW arrays and curve points remain in their existing Working Copy/source representation and are not duplicated into a second giant object.

### 1.4 Analysis Dossier

The Analysis Dossier is generated by `dataset.analyze` for the current Working Copy revision.

It contains the information required to understand the dataset quickly:

- counts;
- deterministic status;
- sample inventory;
- measurement inventory;
- open findings;
- safe corrections;
- true semantic ambiguities;
- evidence/relations/alias coverage;
- compact Results summary.

It is a **summary**, not the entire dataset.

A shared **Experiment Brief** is then derived from those deterministic facts. Its deterministic layer covers scope, performance, comparisons, quality, Design coverage and unresolved questions. If the AI provider is configured, internal `analysis.enrich` may add a provenance-marked scientific interpretation layer. That layer is reused downstream and is keyed to a scientific-input signature, so writing Report/Paper text does not invalidate it. AI enrichment failure never blocks import.

### 1.5 Research Context Pack

The Context Pack is built only when Chat or an AI Action needs context.

It contains only the slice relevant to the current request. It is produced deterministically from the Canonical Store and current UI selection.

A Context Pack may include:

- the shared Experiment Brief (deterministic + optional fresh AI enrichment);
- current page and selection;
- selected sample/device/measurement/group;
- compact measurement values;
- deterministic Results summaries;
- directly relevant findings;
- directly relevant evidence;
- current Design record;
- a bounded report excerpt;
- bounded conversation history.

It does **not** send the full experiment or RAW JV curves by default.

## 2. Import lifecycle

Import is the only experiment entry point.

The app route contract still enters through **Upload & Review**, but an existing browser-local Working Copy is restored automatically when LabFlow is reopened. With no persisted scientific session, Upload & Review is the mandatory ZIP upload gate. The bundled Knowledge Base is available immediately and remains separate from provider/model settings, API keys, UI preferences and experiment state. **Reset session** clears the persisted Working Copy/RAW snapshot and returns to the empty upload gate; it does not alter the bundled library or browser-local Knowledge Base overrides. After a new import the same first page shows the immutable source receipt above the Review workbench; there is no separate Review destination.

```text
Researcher selects ZIP
        ↓
clone original bytes
        ↓
inventory archive entries
        ↓
classify known file families
        ↓
parse deterministic formats
        ↓
resolve canonical sample identities and aliases
        ↓
build measurements and FW/RV relationships
        ↓
build evidence and relations
        ↓
calculate deterministic Results
        ↓
build Analysis Dossier
        ↓
open Review Data
```

### File naming philosophy

LabFlow must tolerate poor laboratory naming.

A filename is provenance, not automatically the scientific identity of a sample.

Canonical sample identity is resolved in this order whenever possible:

1. explicit identity inside the parsed file;
2. known deterministic filename pattern;
3. deterministic directory/naming evidence;
4. otherwise an explicit ambiguity.

Examples such as these may refer to the same sample:

```text
REF1
REF-1
REF_01
Reference 1
```

LabFlow keeps the originals as aliases and stores one canonical entity when the mapping is deterministic. If it is not deterministic, the uncertainty becomes a finding instead of a silent guess.

## 3. Revision and save model

The Working Copy has a scientific revision.

Scientific mutation advances the revision. Examples:

- applying a safe correction;
- applying an accepted AI proposal;
- manual data correction;
- changing Design data;
- changing scientific report content when report state is part of the current Working Copy.

Read-only Actions do not create a scientific revision merely because they ran:

- Chat;
- AI interpretation of Results;
- accepting/rejecting a proposal before applying it;
- opening pages;
- filtering charts.

### Dirty state

The top bar communicates whether the current Working Copy is an **autosaved draft** or an explicit **saved checkpoint**. Autosave provides browser-session continuity; Export remains the operation that creates a new durable LabFlow package.

Only **Save** marks the current internal browser representation as saved. **Export** creates a ZIP explicitly.

Derived exports do not clear dirty state:

- Report PDF;
- Report DOCX;
- NOMAD ZIP;
- other derived files.

### Save never overwrites the upload

Export creates a **new file**. Save persists only the internal LabFlow representation. The uploaded ZIP remains immutable.

## 4. Action philosophy

A researcher Action exists only if it represents a goal a researcher can understand.

A function is not automatically a Action.

These are examples of **internal services**, not public Actions:

- parse one file;
- calculate Results;
- rebuild Canonical Store;
- validate a proposal;
- apply a proposal;
- rebuild Design evidence;
- validate NOMAD mappings;
- store a Action result.

`analysis.summarize` (§6.1.1) is an internal deterministic Action packaged for Settings → Actions inspectability; it is auto-run, not offered as a public researcher action. `analysis.enrich` is an internal automatic AI enrichment that runs only when a provider is configured and stores the optional scientific layer of the shared Experiment Brief.

Settings exposes every executable Action in one Actions catalog. Deterministic, hybrid, Assistant and other AI-backed Actions share the same versioned definitions, runner and browser-local runtime override model; there is no separate AI Helpers surface.

| Goal | Kind | Main outcome |
|---|---|---|
| Analyze dataset | Automatic · deterministic | current Canonical Store + Results + Analysis Dossier |
| Apply safe corrections | Researcher action · deterministic | provable corrections applied to Working Copy |
| Resolve ambiguities | AI assist | correction proposals or unresolved decisions |
| Infer missing design | AI assist | proposals for missing Design fields of one selected experiment |
| Interpret results | AI assist | scientific explanation of deterministic Results |
| Generate report | AI assist | report/paper Markdown |
| Improve report | AI assist | revised current Markdown |
| Prepare NOMAD export | Researcher action · deterministic | canonical→NOMAD mapping + readiness validation |

`assistant.chat` uses the same Context Builder and is visible in Settings → Actions; it remains a non-mutating Assistant capability.

## 5. Action execution model

Action definitions live in:

```text
actions/<action-id>/action.json
```

AI Actions additionally own:

```text
actions/<action-id>/prompt.md
```

Structured AI Actions may reference a schema in:

```text
actions/schemas/*.json
```

### Sequential execution

A run is always finite and sequential:

```text
Action
  ↓
checkpoint 1
  ↓ success
checkpoint 2
  ↓ success
checkpoint 3
  ↓
DONE
```

There is one active run. There is no background queue and no parallel model fan-out.

### User controls

While running:

- **Stop** aborts the active run.

On failure:

- AI checkpoint retry occurs only when the Action declares `max_retries > 0`;
- enabled semantic retries use bounded delays and repeat only the failed work unit;
- provider transport retry is bounded for transient rate limits (`1302`/`1303`/`1305`/`1312`) with `Retry-After` + backoff per provider `rateLimit` policy (quota `1304`/`1308`/`1310` never retries; connection test never retries);
- when a bounded text work unit reaches the provider output limit, an enabled semantic retry rewrites that whole unit with a smaller coherent word range; the cut-off fragment is not stored;
- after declared retries, **Retry checkpoint** may be available;
- unrecoverable provider rate-limit/quota failure stops multi-request sequences instead of advancing through more work units (transient 1305 that recovers within the bounded retries continues);
- retry resumes the failed/pending work, not completed checkpoints.

There is no manual Continue gate between successful checkpoints.

### Provider output

Provider output is closed by default. When opened it must show meaningful streaming data while it arrives and theme-aware formatted Markdown/JSON at completion.

# 6. Detailed Action workflow

## 6.1 Analyze dataset — `dataset.analyze`

**Kind:** automatic / deterministic  
**Provider:** none  
**Prompt:** none  
**Mutation:** no scientific values are changed

### Why it exists

This is the foundation of LabFlow. It establishes what is known before any AI is asked to interpret anything.

### When it runs

- immediately after ZIP import;
- after deterministic or accepted corrections that change scientific data;
- after other scientific mutations that invalidate the dossier/results.

### What it does

Internally it refreshes:

1. canonical identities and aliases;
2. evidence graph;
3. relations;
4. deterministic JV Results;
5. quality/ranking eligibility;
6. findings;
7. safe-fix inventory;
8. true semantic ambiguity inventory;
9. compact Analysis Dossier.

### Output

The current Analysis Dossier for the current Working Copy revision.

### What it must never do

- call a provider;
- invent sample identity;
- change data to make warnings disappear;
- use AI to decide deterministic facts.

### 6.1.1 Analysis Summary Action — `analysis.summarize` (internal, auto-run)

After analysis is fresh, an internal deterministic Action stores the **Analysis Dossier statistics bundle** (`exp.analysisSummary`) on the Working Copy. It is not a public researcher Action: it runs automatically, never needs a trigger, and never mutates scientific fields.

The bundle is the **single deterministic source** for:

- the Results **Compare** per-scan statistics table (FW/RV median±IQR and min–max);
- **Report** statistics and the dynamic figure catalog (overview plots, group overlays and every available JV curve);
- the **NOMAD** derived `analysis.json` (analysis + bundle).

Consumers read the bundle only when `LF.AnalysisSummary.fresh(exp)` — bundle `sourceRevision` matching the Working Copy revision — and otherwise fall back to their own deterministic computation so nothing is ever stale.

Report figures are **rasterized on demand**, never on every render: the picker starts from lightweight metadata and renders previews only for selected figures; PNG previews and DOCX/PDF exports share cached rasters keyed by experiment revision and selection. A Working Copy mutation bumps the revision and invalidates the cache automatically.

## 6.2 Apply safe corrections — `dataset.correct-safe`

**Kind:** researcher action / deterministic  
**Requires:** current Analysis Dossier  
**Mutation:** dataset Working Copy

### Why it exists

Some findings have a mechanically provable correction. These do not require AI or human interpretation.

Examples include:

- excluding a measurement already deterministically blocked from rankings;
- assigning a group derived unambiguously from canonical identity;
- applying explicit REF classification rules;
- other corrections for which target, before, after and evidence are unambiguous.

### Checkpoints

1. **scan** — collect current safe fixes;
2. **apply** — validate each target and apply fixes;
3. **commit** — advance revision and rebuild canonical analysis.

### Provenance

Every applied correction must leave a patch record including as applicable:

- target;
- previous value;
- new value;
- source/method;
- reason;
- evidence;
- reviewer/status;
- timestamp.

### Failure rule

If a target is no longer unambiguous, the correction must fail instead of guessing.

---

## 6.3 Resolve ambiguities — `dataset.resolve-ambiguities`

**Kind:** AI assist  
**Requires:** current deterministic analysis  
**Mutation:** none directly

### Why it exists

Only semantic uncertainty that cannot be established deterministically belongs here.

Typical examples:

- two aliases may or may not refer to the same sample;
- a sample/group mapping is semantically unclear;
- REF/non-REF meaning is not explicit enough for deterministic policy;
- a metadata meaning requires interpretation of human notes.

Technical parser warnings, encoding warnings or missing-file facts are **not** AI ambiguities.

### Context

The model receives a bounded ambiguity Context Pack containing only:

- selected unresolved findings;
- directly linked samples/measurements;
- relevant evidence;
- stable LabFlow IDs.

It does not receive the complete ZIP or full experiment by default.

### Checkpoints

1. **collect** — select true current ambiguities;
2. **resolve** — one bounded structured AI call;
3. **store** — save proposals locally.

### Output

Each ambiguity may become:

- a proposed correction;
- `unresolved` when evidence is insufficient.

AI output is a **proposal**, never an authoritative write.

### Applying proposals

Applying a valid proposal is an internal deterministic service:

1. resolve the target against the current revision;
2. verify the `before` state still matches;
3. verify patch type/value;
4. apply to Working Copy;
5. record provenance;
6. refresh deterministic analysis.

## 6.4 Suggest Design — `design.infer`

**Kind:** AI assist  
**Scope:** one selected experiment  
**Mutation:** none until researcher acceptance

### Why it exists

Design Experiment is intentionally small in the POC. For each experiment LabFlow needs two editable scientific descriptions:

1. **Solution chemistry** — solution/formulation name and role, solutes, solvents and optional composition/additives.
2. **Device stack** — ordered material layers from substrate to top contact.

Source evidence is projected into these structures when it is explicit. The researcher can always add, remove or edit solutions and layers manually; AI is optional.

### Deterministic preparation

Before inference LabFlow knows the selected experiment ID, linked sample names when present, current solution/stack values, source evidence and which of the two Design areas are still absent. The scientific Knowledge Base is a bundled local lookup used only when relevant; no setup, filesystem connection or remote retrieval is required.

### Context

The model receives only:

- the selected experiment and any linked source evidence;
- existing researcher/source solution and stack values;
- whether solution chemistry and/or stack are missing;
- a small set of relevant scientific Knowledge Base records, if local lookup finds any.

A Knowledge Base miss is normal and never blocks the Action. The model may use cautious general inference, but must not invent sample identity, citations or unsupported exact quantities.

### Checkpoints

1. **collect** — build a compact context for the selected experiment;
2. **infer** — request solution chemistry and/or stack;
3. **validate** — bind the output to the selected experiment and sanitize provenance;
4. **store** — save a reviewable suggestion for that experiment.

### Output and acceptance

AI output stays separate from the Working Copy until the researcher accepts it. The Design page shows the proposed chemistry and layer stack graphically next to the editable current values.

- **Accept experiment** accepts one saved suggestion and fills only missing solution/stack values.
- **Accept all suggestions** accepts every currently saved suggestion independently.
- **Discard** removes one suggestion without changing the experiment.
- **Retry** replaces/retries only the affected experiment's suggestion.

Existing source or researcher values are never silently overwritten. Accepted AI values are promoted to researcher-confirmed state and remain editable afterwards.

### Suggest all / resume later

**Suggest all with AI** is a convenience operation, not a separate Design workflow. It selects only experiments that still need solution chemistry and/or stack and do not already have a saved suggestion, then sends bounded batches of at most three IDs. If a provider truncates a batch response, that batch is retried one experiment at a time while completed suggestions remain saved.

Each successful experiment is stored immediately. A content/validation failure may mark only the affected experiment as `Error`, while successful suggestions remain available. A provider throttle is different: on the first HTTP 429 / Z.AI `1305`, the whole sequence pauses immediately, the current untouched batch returns to pending state, and **no later batch is requested in that run**. Completed suggestions remain saved. Running **Continue suggestions** later resumes only experiments that still need suggestions; it never asks the user to restart or discard accepted work.

## 6.5 Interpret results — `results.interpret`

**Kind:** AI assist  
**Mutation:** none

### Why it exists

Deterministic code calculates the Results. AI exists only to explain them scientifically.

### Deterministic source

Results already contain, as applicable:

- FW/RV pairing;
- PCE, Voc, Jsc, FF;
- hysteresis;
- ranking eligibility;
- best-by-sample;
- REF/non-REF rankings;
- group statistics;
- anomalies/warnings;
- curve summaries.

### Context

AI receives a compact Results Context Pack:

- summary;
- top REF/non-REF;
- best-by-sample subset;
- anomalies;
- relevant findings.

It does not calculate replacements for deterministic metrics.

### Output

Scientific Markdown interpretation stored separately from source Results.

---

## 6.6 Generate report — `report.generate`

**Kind:** AI assist  
**Mutation:** Report document only

### Why it exists

The model is useful for scientific prose composition, not for inventing measurements.

### Inputs

A deterministic Report Context Pack includes:

- requested document kind;
- deterministic Results summary;
- Design summary;
- findings;
- provenance;
- selected figure configuration;
- other bounded scientific evidence.

### Checkpoints

1. **collect blocks** — deterministically plan bounded document sections;
2. **draft blocks** — model writes each requested section using the shared Experiment Brief and bounded evidence;
3. **merge/store** — ordered sections become the current Report/Paper editor content.

Fresh imports keep both Report and Paper empty. Drafting occurs only after the researcher explicitly chooses Draft.

### Source-of-truth rule

The current Report Markdown editor is the single textual source used by Report exports. It supports standard inline `$...$` and display `$$...$$` LaTeX. Preview typesets formulas locally; `.tex` preserves them and DOCX/PDF render display equations into the exported document. PDF/DOCX must not silently regenerate different prose during export.

---

## 6.7 Improve report — `report.improve`

**Kind:** AI assist  
**Mutation:** Report document only

### Why it exists

Revision is the same conceptual Action regardless of whether the researcher wants to improve Methods, Results, Discussion, scientific review or general style.

### Inputs

- current editor Markdown;
- explicit improvement mode;
- deterministic scientific evidence pack.

### Output

Revised Markdown returned to the same editor/source of truth. Common aids (for example tighten, clarify, evidence check) and Report/Paper-specific aids are modes of this Action. Long documents are split by section/block so each model call receives the relevant text plus the same bounded scientific basis.

The Action must preserve factual consistency with deterministic Results and provenance.

---

## 6.8 Prepare NOMAD export — `nomad.prepare`

**Kind:** researcher action / deterministic  
**Provider:** none  
**Mutation:** no scientific source mutation

### Why it exists

NOMAD is a mapping/export problem, not an AI readiness problem.

### Single mapping principle

One Canonical → NOMAD mapping plan must power:

- NOMAD page;
- local validation;
- generated `experiment.archive.yaml`;
- exported `metadata/mapping_plan.json`.

There must never be separate UI mapping and export mapping implementations.

### Checkpoints

1. **prepare** — build explicit field mapping;
2. **store** — retain the revision-scoped mapping plan;
3. **validate** — run authoritative local validation.

### Mapping row

A mapping should be inspectable in terms such as:

```text
LabFlow source → NOMAD field → current value → required? → status
```

### Readiness

- required missing mappings block staging;
- optional missing values remain visible;
- AI never declares NOMAD readiness.

Scientific mutation invalidates stale mapping/staging.

# 7. Assistant Chat

`assistant.chat` is an AI Action exposed in Actions. Its conversation/output settings remain separate, but its executable prompt/contract is edited through the same Action runtime editor. It is read-only with respect to scientific state.

The chat surface has one durable user message and one durable Assistant message per turn. The Assistant message is created before the request and that same message moves through `requesting → streaming → complete`, `error` or `cancelled`; streaming never creates a second reply. Its small transient spinner is visible only before useful response content exists. The first usable content replaces it in place, and completion, error, cancellation and cleanup all close the transient state. A failed message exposes Retry on that same turn.

The conversation is the panel's only vertical scroll region. Page/selection context appears once in the header, completed provider reasoning and telemetry live in a closed **Details** disclosure, and Action results appear as compact system events rather than Assistant replies. Auto-scroll follows output only while the researcher remains near the bottom; otherwise a **New response** control preserves the current reading position. Only complete user/Assistant turns enter bounded conversation memory; system events, errors and interrupted turns do not.

## Deterministic Assistant context

The Assistant builds one bounded read-only context locally from the current page/selection, recent completed conversation turns, focused Canonical samples/measurements/results/findings/evidence and the active Design, Report or NOMAD slice when relevant. A small local Knowledge Base lookup may add LabFlow help or scientific background when it matches the question; a miss is normal and adds no delay beyond the local search.

There is no LLM tool-planning round before the answer. One user turn therefore maps to one provider request. This keeps latency, rate-limit pressure and lifecycle handling predictable while preserving the current Working Copy as the factual source of truth. The Assistant cannot invoke write Tools or mutating Actions.

Examples:

### Question from Results

> Why is Treatment B worse than REF?

The deterministic chat context should include the relevant Results, measurements, findings, Design and evidence for the comparison instead of unrelated files.

### Question from Design

> What is missing for NEW-1A?

The Assistant should retrieve the selected sample/Design and linked measurements/evidence through the corresponding read Tools.

### Question from NOMAD

> What blocks the export?

The Assistant should read the current NOMAD state and only the evidence needed to explain missing mappings or validation warnings.

## Budgeting

Chat context remains bounded separately. Output tokens are resolved from the active provider/model capability, then optionally reduced by Assistant, Action or provider-level caps. `0` means automatic; LabFlow does not inject a fixed 8k ceiling.

# 8. Review Data workflow

Review must make three categories obvious.

## Deterministic findings

Shown immediately after import.

## Safe corrections

Provable fixes can be applied individually or in bulk. Applying them modifies only the Working Copy and immediately refreshes deterministic analysis.

## Ambiguities

Only true semantic ambiguity is offered to AI. AI proposals can be applied individually/bulk only after deterministic validation.

## Human decisions

If neither code nor AI has sufficient evidence, the item remains visible as needing researcher decision. It must not disappear into a count.

# 9. Results workflow

Results are always deterministic and independent of Design reconstruction.

The page must remain useful even if Design is incomplete or AI is unavailable.

Expected capabilities include:

- Overview;
- rankings;
- REF/non-REF separation;
- all measurements;
- warnings/anomalies;
- JV Analyzer for one measurement: FW/RV curve, deterministic parameter deltas, RAW scan-integrity checks and descriptive FW/RV separation;
- Overlay with its own independent multi-measurement selection for direct visual comparison;
- group comparison;
- responsive statistics tables;
- optional AI interpretation layered on top.

`ORIGINAL_REQUEST/jv_analyzer.html` is the functional reference for useful JV analysis behaviour.

# 10. Experiment Design workflow

Design is researcher-first.

```text
Deterministic known data
        +
Researcher edits
        +
Explicit Knowledge Base reuse
        +
Optional AI inference for missing fields
```

Use the UI Kit **Single-experiment Design** pattern:

- experiment/device coverage rail/card board with explicit completion state;
- compact experiment navigator with `Ready`, `Needs suggestion`, `Suggested`, `Accepted`, and `Error` states;
- graphical **Solution chemistry** with direct solute/solvent/formulation editing;
- graphical **Device stack** with direct ordered-layer editing;
- optional source evidence as progressive disclosure;
- one reviewable AI suggestion for the selected experiment, when present.

AI must never overwrite user-confirmed values silently.

Knowledge Base management is available without loading a ZIP and has no setup step. Bundled records are searchable immediately; create/update/delete and JSON import create browser-local overrides, while JSON export provides a portable snapshot. Existing legacy browser records are migrated once into the same override format. Management and lookup are read-only with respect to the Working Copy; only acceptance of a validated AI Design proposal can fill scientific fields.

Design keeps one convenience command, **Suggest all with AI**, but no complex completion workflow. It prepares independent reviewable suggestions in bounded batches; the researcher accepts one experiment or all saved suggestions explicitly. Errors and Stop are resumable per experiment.

# 13. Invalidation rules

Derived state must identify the Working Copy revision it belongs to.

Examples of derived state:

- Analysis Dossier;
- Results interpretation;
- Design proposal;
- NOMAD mapping plan/validation;
- other AI proposals.

If the scientific Working Copy changes, stale derived data must be refreshed or explicitly invalidated. It must never silently masquerade as current.

# 14. What must remain simple

Do not add:

- a second editable experiment state;
- server-side workflow orchestration;
- background AI jobs;
- provider queues;
- parallel model fan-out;
- manual Continue gates between successful checkpoints;
- AI calculation of deterministic metrics;
- AI NOMAD readiness decisions;
- automatic rewriting of original files;
- hidden autosave that changes the saved revision;
- giant full-experiment AI payloads by default.

When a feature seems to require one of these, first ask whether it can instead be implemented as:

```text
deterministic service
        ↓
Canonical Store
        ↓
bounded Context Pack
        ↓
optional AI assist
```

# 16. Current interaction contracts (2026-08-14)

## Upload & Review

Upload is mandatory and Review is not a second route. `experiment-understand` is retained only as a compatibility alias to `experiment-import`. After successful import the first page renders the source receipt and deterministic-first review together.

## Report/Paper figures

`report.figureSelections.lab` and `report.figureSelections.paper` are independent. Legacy `report.figureSelection` is migrated to both once and then kept only as the active-document compatibility alias. Preview, Context Pack and export always read the active document selection.

## Internal edit provenance

Working Copy patches and Report/Paper edit provenance remain bounded internal metadata. There is no separate Changes workflow page; current state is authoritative for the UI and Assistant, while provenance remains available to exports and diagnostics.

## Provider output limits

The AI transport resolves model capabilities and caches them by provider/endpoint/model. Exact output maxima are preferred; when a context ceiling is available, preflight reserves the Action target output rather than its full theoretical ceiling, compacts the Context Pack, and may relax only as far as the declared minimum valid output before reporting a real overflow. The final transport budget is recalculated from the fitted input size. Unknown limits remain unknown and the token parameter is omitted. Settings can force a lower global cap, and Assistant can force a lower chat-only cap; zero means automatic.

For Report/Paper and other word-sized work units, a known provider or researcher ceiling is applied to `target_words`, `min_words` and `max_words` before the Context Pack is built. If a provider still returns `finish_reason: length` (for example because hidden reasoning consumed part of the allowance), the declared bounded retry requests one complete shorter rewrite instead of resending the same impossible target or storing partial prose.

Each AI checkpoint declares whether it needs thinking (`off`, `auto` or `on`). Settings' `Follow each Action` mode preserves that policy; force Off/On is an explicit global override. The transport reconciles it with model capability (`none`, `optional`, `required`, `unknown`): it does not enable thinking on a non-reasoning model or disable a reasoning-required model, and it only applies fields declared by the active provider adapter. Local LM Studio metadata uses the actually loaded instance; Ollama uses native model metadata when available, while llama.cpp uses its OpenAI-compatible served-model catalogue and conservative Action caps. Provider discovery runs only from explicit **Detect**. Connection testing is a separate minimal request and never changes the selected model; opening Settings and editing fields cause no provider request. The complete compatibility contract is documented in [`docs/specs/AI_PROVIDERS.md`](specs/AI_PROVIDERS.md).

Token optimization remains conservative and Action-specific. Compact scientific Actions use lower expected targets; complete Design JSON and document blocks retain generous hard ceilings. Context construction removes duplicate evidence aliases before trimming unique facts, and prompts state each constraint once. Speed improvements must not remove evidence, reduce the requested scientific depth, store truncated output or weaken deterministic validation.

## Assistant streaming

Chat displays one transient semantic state before content: waiting, thinking, provider request or read-tool activity. Raw SSE chunk/event/byte counters stay in logs. On the first useful streamed content the transient indicator is removed and the existing Assistant body is updated incrementally. Reasoning never enters the answer body; after completion it is available only in the closed Details disclosure alongside model/provider, latency, TTFT, usage and throughput metadata when available.


## Design and document finishing controls

Design uses one selected-variant completion at a time. Safe suggestions are applied immediately; the page shows only review decisions and unresolved fields that still need attention.

Report/Paper writing helpers run section-by-section when `All` is used. Each work unit has a target scientific depth. Figure selection is independent for Report and Paper and is applied through the figure picker before preview/export.
