# AI assistance

AI is optional for the scientific core. Parsing, normalization, validation, calculations, Results analysis, export preparation, Cabinet lookup and Knowledge Base lookup remain deterministic.

## Assistant pipeline

The Assistant is read-only and deliberately split into routing and answering. LabFlow does not hard-code natural-language phrases for particular languages.

```text
explicit slash command -> LOCAL, zero tokens
natural language -> tiny language-agnostic router
                 -> deterministic facts/state
                 -> LOCAL when those facts answer the request
                 -> bounded answer model only for interpretation
```

The intent router sees only the user message plus the current page/view. It returns a tiny structured decision: intent, target, whether reference knowledge is needed, whether Cabinet is needed, whether the question depends on the previous turn, and an optional compact retrieval query. It does not answer the research question.

The router is the only intent authority and stays a separate call for predictability. To keep small models cheap, an identical question asked on the same page/view reuses the cached routing decision (no router call), and an entity-free follow-up can deterministically reuse the previous intent instead of falling back to clarification. The cache is session-only and is never saved with the experiment.

Conversation memory is session-only as well: LabFlow keeps the current **focus** (the sample, measurement, group or Design experiment the conversation is about), the last intent/target, and a bounded router cache. Focus is resolved from canonical LabFlow identifiers and the current page selection, never from a language-specific keyword list. The focus is shown under the message **Details** and disappears on Reset session or Clear conversation.


When a routed request is factual, the final response is generated by LabFlow from canonical state. The badge is **LOCAL · LLM router** because one small provider call was used for language-agnostic intent classification, but no answer-generation call occurred. Explicit commands such as `/missing`, `/summary`, `/status`, `/best`, `/anomalies` and `/count measurements` remain **LOCAL · 0 tokens**.

Interpretive or scientific requests make one additional bounded answer request. That request receives only a small task-specific fact pack. The Assistant never opens an Action Totem; chat progress stays inline and technical telemetry stays under the message's **Details**.

## Small-model budgets

The intent router is non-streaming, temperature 0, reasoning off, and limited to 96 output tokens. The `assistant.chat` answer step has a 1400-token input ceiling, 120-token target output and 280-token maximum output. LabFlow compacts facts rather than expanding toward the provider's full context window.

Normal answer context may contain resolved scope, focused deterministic experiment/Results/Design facts, up to a few explicitly requested Cabinet/KB references, and at most one previous user/assistant turn when the router marks the message as a follow-up. It does not include the full experiment, Workspace dump, Action catalog, Action history or long chat history.

Facts are chosen by intent and target first, with the open page only a secondary signal, and the request also carries a bounded flat `key=value` digest of the most important scalars. Small models read that flat digest more reliably than nested JSON, while LabFlow keeps the JSON body for validation and telemetry.

## Answer format and grounding

The answer request uses a fixed ASCII envelope, while the prose stays in the researcher's language:

```text
ANSWER: the concise answer.
BASIS: comma-separated fact keys used, e.g. facts.results.summary, facts.focus
UNKNOWN: what could not be determined (optional)
```

LabFlow parses the envelope tolerantly. `BASIS` keys must exist in the supplied pack, and every number in `ANSWER` must come from the supplied facts or from the question (rounding is accepted). An answer whose numbers are entirely unsupported is replaced by the deterministic fallback instead of being shown as grounded, and a partial mismatch is reported under **Details → Answer grounding**. Unsupported `[KB:<id>]` citations keep the existing rejection behavior.


## Reasoning / thinking

Assistant has **Prefer off** (default), **Automatic**, and **Prefer on**. Provider-native reasoning fields and compatibility tags such as `<think>…</think>`, `<thinking>…</thinking>`, `<analysis>…</analysis>` and `<reasoning>…</reasoning>` are separated from the visible final answer, including during streaming. Diagnostic reasoning is available only under **Details → Reasoning details** and is never treated as scientific evidence.

## Knowledge and grounding

Design and Assistant use different KB views. Design receives compact bibliography-free candidates and structured `design_hint` data. The Assistant receives source-bearing KB entries only when the router explicitly says reference knowledge is needed. Retrieval is performed from the router's short scientific search query rather than from a dump of current page JSON.

A model may cite only exact KB ids supplied in that answer request, as `[KB:<id>]`. LabFlow validates citations before rendering. Unsupported citations reject the answer instead of turning invented references into apparent evidence. KB material is background knowledge, never proof of what the current experiment used or measured.

## Other provider-backed Actions

`dataset.resolve-ambiguities` receives only unresolved semantic findings and linked evidence. `design.infer` resolves experiment evidence, Cabinet and KB candidates first, then asks the model only for Design domains still unresolved. Results interpretation/comparison and export preparation are deterministic and make no provider request.

## Researcher control

Provider output never silently rewrites canonical scientific state. Suggestions remain validated/reviewable, and unknown values may remain unknown.
