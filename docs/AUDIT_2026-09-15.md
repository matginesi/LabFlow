# Engineering audit · 2026-09-15

This document is a historical audit snapshot, not an evergreen specification. Current contracts live in `ARCHITECTURE.md` and the feature specs.

## Findings addressed in r12

The audit concentrated on maintainability across scientific data, Cabinet, Knowledge Base, AI/provider integration, Actions and Assistant.

Key outcomes:

- preserved one `ExperimentData` scientific aggregate rather than introducing a central “mega model”;
- added a cross-module structure catalog so ownership/persistence can be inspected without duplicating runtime models;
- made Cabinet kinds/fields/capabilities registry-driven and removed UI-owned duplicate definitions;
- moved Cabinet → Design writes behind `DesignModel` and retained detached-copy provenance semantics;
- kept the KB intentionally simple as bundled + browser-local JSONL instead of introducing a database/vector store without need;
- clarified ActionData, active Action run and Assistant conversation as separate persistence/runtime concerns;
- strengthened architecture/source-hygiene validators and added structure/Cabinet boundary tests;
- corrected Cabinet validation so stack-specific layer completeness is enforced on stacks rather than substrates.

## r13 review-readiness hardening

The follow-up pass treated documentation and comments as part of the engineering contract rather than presentation material. It:

- reorganized documentation into authoritative architecture/specification, researcher guides and engineering references;
- rewrote module comments around responsibility, ownership boundaries and non-obvious invariants instead of narrating syntax;
- removed repetitive test-file commentary and historical CSS “fix/polish” annotations that added no contract value;
- added contributor, code-review and security-posture references without claiming production guarantees the POC does not provide;
- made the generated Action runtime matrix part of the release stale-artifact gate;
- verified documentation front matter and relative links during the review pass;
- preserved CSS behavior exactly while reducing comments to file-level ownership notes.

The goal was not maximum documentation volume. The goal was that a new reviewer can identify the source of truth, mutation owner, persistence class, AI authority boundary and verification path without reconstructing them from implementation details.

## Validation state at audit close

The distributable release gate passed using self-contained tests and synthetic Upload & Review regression data. Private real-dataset suites required local `TEST_DATA` archives not shipped in the reviewed ZIP. Browser automation in the audit environment was separately blocked from navigating localhost by environment policy; this was recorded as an environment limitation rather than an application failure.

## Review posture

The architecture deliberately favors explicit ownership and small registries over framework-heavy indirection. Future work should preserve that property: add complexity only when it removes a demonstrated duplication, enforces an invariant, or enables a required capability that cannot be expressed cleanly in the current model.
